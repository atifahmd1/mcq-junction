3. Administrative UI Workflows Implementation

Module 2A: Protected Admin Layout Shell & Overview Dashboard src/app/admin/layout.tsx & page.tsx

Authentication Guard: Server-side layout enforces assertAdminSession(). Unauthenticated callers are redirected to /login; authenticated non-admins receive a structured 403 Forbidden screen with their email and role clearly displayed.

Operational Telemetry: Dashboard aggregates real platform metrics via Prisma queries: total exam papers, published papers, total question bank occurrences, and total submitted attempts. Renders a recent exam papers table with active status badges.

Module 2B: Exam Paper Management Table src/app/admin/papers/page.tsx

Search & Status Filtering: Server Component supporting URL search params for query string search (title and description) and status filtering (ALL, DRAFT, IN_REVIEW, VERIFIED, PUBLISHED, ARCHIVED).

Bounded Pagination: Enforces safe integer bounds (default 10, max 50 per page). Zero unbounded memory scans or client-side secret exposure.

Contextual Workflow Links: Dynamically surfaces action buttons based on paper status: Sequence Editor for draft/review papers, Publication Review for verified papers, and Adjudication Dashboard for published papers.

Module 2C: Question Sequence Editor (Atomic SQL CASE Reordering) src/app/admin/papers/[paperId]/sequence

Atomic Swapping: Reordering adjacent questions in a paper is performed through swapQuestionSequenceAction() calling swapQuestionSequence(). Executes an atomic PostgreSQL CASE update in a single statement: 

UPDATE paper_question_occurrences
SET sequence_number = CASE
  WHEN id = $1 THEN $seq2
  WHEN id = $2 THEN $seq1
END
WHERE id IN ($1, $2) AND paper_id = $paperId;

Constraint Collision Immunity: In PostgreSQL, unique constraints evaluate after the statement completes. This single-statement swap prevents transient unique constraint collisions on (paper_id, sequence_number).

Immutability Guard: Enforces that publish_status !== 'PUBLISHED', raising MCQJ_IMMUTABLE_ERROR (400) if an admin attempts to reorder a published exam paper.

Module 2D: Publication Review Modal (6-Gate Quality Checklist) src/app/admin/papers/[paperId]/publish

Pre-Flight Checklist: The publication screen evaluates 6 mandatory quality gates before enabling publication:

  1. Verification Status: Paper status must be strictly VERIFIED.
  2. Question Count: Paper must contain at least 1 question occurrence ($\ge 1$).
  3. Sequence Contiguity: Sequence numbers must be strictly contiguous from $1 \dots N$ without gaps or duplicates.
  4. Editorial Review: 100% of question representations must have is_verified = true.
  5. Official Answer Key: At least one active answer key version must exist for the paper.
  6. Booklet Series: At least one booklet series (e.g. Series A) must be configured.

Double-Confirmation Safety Modal: Prevents accidental publication by requiring the administrator to type the exact exam paper title before the "Confirm & Publish" button is enabled. Dispatches to publishExamPaperAction(), invoking the advisory-locked database procedure fn_publish_exam_paper().

Module 2E: Answer-Key Adjudication & Historical Two-Tier Ledger src/app/admin/papers/[paperId]/adjudication

Controlled Key Re-evaluation: Dedicated adjudication dashboard for live, published exam papers. Displays current active answer key items and total submitted student attempts.

Audit Trail & Justification: Enforces selection of the target answer key version and entry of a mandatory adjudication rationale (minimum 10 characters).

Two-Tier Ledger Guarantee: Double-confirmation modal explicitly warns the administrator: "Active evaluations will be updated to the new key version while historical v1 evaluations remain permanently immutable in the audit ledger."

Historical Re-evaluation Log: Displays a complete immutable log of prior re-evaluations with version increments, processed attempt counts, timestamps, and executing administrator IDs.

6. Security Hardening & Zero-Knowledge Hygiene

  • Strict Role-Based Access Control: Server-side layouts and actions assert valid JWT sessions and enforce role === Role.ADMIN directly against the authoritative PostgreSQL users table.

  • Ephemeral Database Passwords: Integration tests generate ephemeral UUID passwords dynamically (test_pw_<guid>) and unset them after test execution. Zero plaintext passwords exist in repository source or commit history.
  • Remote Database Safety: Remote Supabase production database was preserved completely untouched. All tests executed against disposable Docker containers.
