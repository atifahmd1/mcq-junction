3. Formal Phase 4 Authorization Contract

The architecture supports three distinct execution paths. Security Definer procedures inside PostgreSQL enforce rigorous Gate 0 identity checks to prevent caller spoofing:

Key Security Mechanics

  • SESSION_USER vs CURRENT_USER: In PostgreSQL SECURITY DEFINER functions, CURRENT_USER always resolves to the function owner (postgres). Evaluating CURRENT_USER creates an authorization bypass vulnerability. Guards inspect SESSION_USER and auth.role() instead.
  • Anti-Spoofing Assertion: When called via PostgREST, Guard 0.2 verifies that p_admin_user_id = auth.uid(), preventing any user from publishing on behalf of another user ID.
  • Mandatory Audited Admin Identity: Headless service-role requests via PostgREST (Path C) are intentionally rejected by Guard 0.5 because publications and re-evaluations must be attributed to an authentic administrator in the audit ledger.
