Executive Summary

Phase 4 Module 1 delivers the production application service layer, cryptographic server-side authorization guard, strict RFC 4122 v4 input validation boundary, and Next.js App Router Server Actions for MCQ Junction. Critically, this phase closes the PostgREST public exposure risk by revoking privileged procedure execution from authenticated callers via forward-only SQL migration.

Operational Security Invariant
Administrative stored procedures (fn_publish_exam_paper and fn_reevaluate_paper_attempts) can no longer be triggered directly over Supabase PostgREST HTTP endpoints by authenticated students. All mutations must execute through the Next.js Server Action path, which verifies session cryptography, enforces ban/suspension status, queries the application database role, and explicitly binds verified administrator IDs.

3. Security Hardening Analysis: Closing Privileged PostgREST Exposure

In standard PostgreSQL configurations, routines created inside the public schema inherit default execute privileges granted to the pseudo-role PUBLIC. In a Supabase environment, PostgREST inspects routines in schemas exposed to the API and automatically registers HTTP endpoints at /rest/v1/rpc/{function_name}.

While Gate 0 in the database kernel checked for caller authorization, exposing privileged procedures to the HTTP layer creates an unnecessary attack surface. Migration 20261012140000_revoke_authenticated_privileged_rpc explicitly revokes execution permissions from PUBLIC, anon, and authenticated, restricting access to service_role and postgres. 

-- Catalog verification query in DB-19:
SELECT routine_name, grantee, privilege_type
FROM information_schema.routine_privileges
WHERE routine_name IN ('fn_publish_exam_paper', 'fn_reevaluate_paper_attempts')
  AND grantee IN ('PUBLIC', 'anon', 'authenticated');
-- Returns 0 rows. Verified in DB-19.1.
